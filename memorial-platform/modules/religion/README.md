# 宗教与文化目录

## 1. 现在的状态：一个祭奠方式都提供不了

播种数据只包含**分类条目**和**动作标识**：14 个宗教分类、12 个文化传统、
15 个祭奠动作的稳定标识。

**`ritual_versions` 表是空的。** 由于任何祭奠方式都必须通过一个已发布版本才能
被家属采用，当前平台对任何主页都不提供任何祭奠方式。

这是刻意的，不是未完成。文档 11 §4 规定顾问资格、可接受资料来源、审核人与
发布人是否必须分离，这些都尚未确定。在此之前编造宗教规则会违反文档 05 §6 和 §9。

**这里不需要工程决策，需要的是真人顾问。**

## 2. 分类条目不是教义声明

一行 `religions` 记录只表示「这个传统存在」。它不表示这个信仰教导什么。

`adminLabel` 是给管理员看的英文工作标签。**面向读者的名称只来自经审核的翻译**，
永不来自这个字段。

宗派（`denominations`）单独建模，因为实践在宗派之间的差异远大于顶层分类暗示的程度。
把某一个宗派的做法说成整个宗教的规则，正是文档 05 §1 禁止的失败模式。

## 3. 发布门槛

`publishRitualVersion()` 的每一道检查都是在拒绝「做出一个无人负责的、
关于他人信仰的论断」：

| 门槛 | 缺了会怎样 |
|---|---|
| 至少一条资料来源 | 该规则变成平台自己对某信仰的断言 |
| 明确适用范围 | 它会无声地代表全世界所有信徒发言 |
| 署名审核人 | 责任无法追溯 |
| 人工审核的翻译 | 读者会把机翻措辞当作经过考量的表述 |
| super_admin 权限 | 日常审核门槛不足以承担这种论断 |

**已发布版本永不修改。** 家属采用的是某个具体版本；在他们脚下改写会让
主页提供的内容变化而无人问过他们。更正的方式是新建版本。

**停用版本会保留，并通知采用过它的主页所有者**，由所有者自己选择替代方案 ——
文档 05 §5 禁止平台替他们换掉。

## 4. 变异验证记录

- 去掉「至少一条来源」→ 1 条测试失败；
- 去掉「人工翻译」→ 1 条测试失败。

## 5. 下一步需要什么

在任何 `ritual_version` 被创建之前，需要文档 11 §4 的以下决策：

1. 顾问资格与利益冲突声明；
2. 可接受的资料来源类型；
3. 审核人与发布人是否必须为不同的人（`authoredByUserId` / `reviewedByUserId` /
   `publishedByUserId` 三列已就位，答案确定后无需迁移即可强制）；
4. 宗派争议的标注格式；
5. 复审周期与紧急停用权限。
