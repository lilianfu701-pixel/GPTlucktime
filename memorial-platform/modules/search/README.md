# 搜索

## 1. 隐私保证在 SQL 里，不在应用层

`searchMemorials()` 的可见性条件**联表查询 `memorials` 的活行**，
不查 `search_documents` 里的任何副本。

这是整个设计的核心。家属把主页切成仅受邀后，worker 清理索引之前会有一个窗口 ——
如果过滤依据的是索引里的可见性副本，这个窗口就是「已经私密但仍能被搜到」的泄露期，
正是文档 02 §5 禁止的情况。

`search_documents` **刻意不存 visibility 字段**。存了就会引诱后来的人去过滤那个副本，
看起来完全正确。

在应用层拿到结果后再过滤更糟 —— 数据已经离开数据库了。

**变异验证**：去掉 SQL 里的 `visibility = 'public'` 条件，3 条测试立刻失败，
其中一条正是「索引滞后不泄露」。

## 2. 为什么用子串匹配而不是全文索引

首发语言里多数不按空格分词。`to_tsvector` 找不到「王明华」里的「王明」，
家属搜自己亲人会一无所获。

所以用 `LIKE '%...%'` 保证结果正确，GIN trigram 索引负责加速。

**已知伸缩限制**：trigram 索引对 3 字符以上的查询生效。更短的查询（中日韩常见）
无法走索引，退化为扫描。这一点没有被掩盖 —— 数据量上来后需要换方案
（例如为 CJK 单独建 2-gram 列，或引入专门的搜索引擎）。

另有一处 PostgreSQL 限制：`array_to_string(...)` 是 STABLE 而非 IMMUTABLE，
不能用于索引表达式。所以索引器把别名和地点**折进 `normalized_text`**，
一个索引覆盖全部；数组列保留用于结构化过滤和展示。

## 3. 不可搜索的名字

家属可以记录曾用名但不让它被搜到（文档 07 §4）。索引器只收 `searchable = true` 的名字，
**每次重建索引都重新执行这个过滤** —— 否则某次重建就会悄悄把它放出去。

## 4. 结果里没有的东西

搜索结果只有：memorialId、slug、姓名、生卒年份、国家代码。

没有所有者、没有联系方式、没有亲属关系声明。有测试断言字段集合精确匹配。

展示的姓名读自 `memorial_names` 而非索引 —— 索引里是归一化后的匹配键，
而人的名字应该按家属书写的样子显示。

## 5. 反抓取

- 单页最多 50 条；
- **翻页深度上限 200**：找一个人在前几页就找到了，走到第 5000 条的是在建列表
  （文档 06 §9 把批量抓取列为威胁）；
- 空查询直接拒绝 —— 那等于请求列出全部公开主页；
- 单字符查询拒绝，两字符放行（中日韩姓名可以只有两个字）。

排序按发布时间倒序，**刻意不按热度** —— 文档 01 §4.3 禁止任何让一个家庭的主页
排在另一个之上的机制。

## 6. 重复检测只记录，不合并

`findDuplicateCandidates()` 返回候选，然后就结束了。它不合并、不隐藏、
不阻止创建、不排序。

- **合并是人的决定**（文档 03 §7）：合并两个家庭的页面在要紧的地方是不可逆的，
  而一个分数不是证据；
- **不阻止创建第二个主页**：在悲痛中创建第二个主页的家属，应该被展示第一个，
  而不是被一个他们看不见的数字拦住；
- **分项分数分开存**：审核者要能看出「两条记录只是重名，其他都不一致」；
- **两个未知日期不算一致**：否则每个信息稀疏的主页看起来都像其他所有主页。

## 7. 运维注意

`drizzle-kit migrate` 在迁移失败时**静默退出 0**。本任务中 `CREATE INDEX ... array_to_string(...)`
因 IMMUTABLE 限制失败，而命令报告成功、journal 未推进。

部署后不要只看退出码，要核对 `drizzle.__drizzle_migrations` 的条目数。
